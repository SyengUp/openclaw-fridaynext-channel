## 真实链路与根因

- 请求 `5155287C-DC7D-4A1D-B9B4-40985A04A20E`，逻辑会话 `BE6C6DD9-A670-4835-8BDA-43D35CCD77C4`。

- 手机发送账本的 text／displayText 都是原提示 28 个字符，附件有两份。OpenClaw 原生用户记录为 2970 个字符，包含媒体标记及文件提取块。
- 插件历史页和全文详情返回 2708 个字符，包含 `<file name="…" mime="text/markdown">` 与外部内容信封。手机 `history.message` 同样为 2708 个字符，`user.content` 仍为 28 个字符，UI 缓存与截图一致；最终回复只有一条。

写入点是 OpenClaw 的媒体理解：把提取的附件正文追加到模型输入。插件历史 normalizer 原来只移除了媒体路径标记，文件块继续进入规范历史，随后覆盖 App 的用户展示正文。发送流程没有把文件正文当作用户输入持久化。

## 修复边界

- normalizer 在截断前移除与原生 document 媒体事实的文件名／MIME 相符、完整且位于末尾的提取块；附件引用保留。不处理助手正文，不删除无媒体事实、名称／MIME 不符或未闭合的文字。
- 当前会话中唯一且明确归属的附件命令提供原始正文，覆盖模型输入的追加内容；用户自己输入相同 `<file>` 标签仍可完整展示。不同设备同请求 ID 出现歧义时不采用该来源，没有附件或缺字段的旧命令也不作为来源。
- 历史页、全文详情和恢复快照共用规则，保留历史预算与全文查询的区别，保持消息、请求和运行身份。模型输入不被修改，文件仍供 Agent 使用。
- 改动仅在插件及其测试／版本／隔离验证入口；App、Kit `0.1.2` 和 OpenClaw core 无需修改。
